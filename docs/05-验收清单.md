# 验收清单

## A. 自动验收（零模型费用）

`scripts\run-tests.ps1`：155 项单元测试、45 项备份恢复测试、64 项 Desktop 安装/卸载测试、23 项官方 CLI 配置实载检查及 29 个官方运行时集成场景（`it25` 仅在 Windows 运行，其他平台自动跳过）。模型与档位断言读取当次配置，不把默认模型写成固定要求。

| 场景 | 验证的要求 |
|---|---|
| it01-happy-path | plan 讨论 → 绑定 `plan_id` 派发（code 档位）→ 成员先读参考再写 → 安全门按 `roles.gate` 的模型与档位审查 team_dispatch 与 write（无工具）→ delivery 讨论 → `DELIVERY: approved`；领队无写工具；成员无领队工具；门请求不含对话历史 |
| it02-gate-deny | 安全门拒绝 → 文件未写入，成员看到拒绝原因，回执记录 |
| it03-rewrite-caught | 外层插件在审查后改写路径 → 门按改写后的参数判定并拒绝，两条路径都未写入 |
| it04-review-failure | 审查返回 HTTP 500 / 非 JSON → 重试后仍失败 → 拒绝（fail-closed） |
| it05-hard-rules | 未读参考先写、写全局参考、写 `.leaderteam`/`.git`/`.agents`/`AGENTS.md`、成员调用 `team_dispatch` 均被拒；读完参考后可写；硬规则不产生模型请求 |
| it06-plan-required | 无通过的 plan 讨论或缺少有效 `plan_id` 时写入型成员不能派发；只读侦察可以 |
| it07-quota | 额度耗尽的模型被拒并说明；改选后按所选模型/档位执行，不静默替换 |
| it08-arbiter | A 一直 approve、B 一直 revise → 3 轮各 2 次请求 → 按 `roles.arbiter` 的模型与档位裁断恰好 1 次 → 采纳 B；第 2 轮双方互见上一轮意见 |
| it09-agreement-resume | 第 2 轮 A 调用失败 → 返回可续跑错误 → 续跑只补问 A，第 1 轮不重复 |
| it10-resume-member | 中断后 `--session-id` 恢复，成员仍是原模型与 code 档位，能继续写 |
| it11-fail-loud | 配置无效 → DSH 拒绝启动，没有任何模型请求 |
| it12-read-boundary | 外部必读资料派发被拒；成员越界读取、通过目录联接读取或写入越界被拒；工作区和全局参考可读 |
| it13-read-completion | 参考文件仅读一页或留有缺页时禁止写入，分多页读完后允许写入 |
| it14-core-missing | 核心行缺失/disabled → required executor 缺失，DSH 拒绝启动，零模型请求 |
| it15-standard-scope | 普通 standard agent 真实写入文件：无安全门回执、无 team 结构 |
| it16-executor-readiness | 就绪依赖隔离时 required executor 无法启动：非零退出、零模型请求 |
| it17-leader-model | 会话实际模型不是 `roles.leader`：全部团队工具拒绝并给出应切换的模型，零门/讨论请求、零成员 |
| it18-parallel-members | 两个写入成员（不同模型/档位）同时运行（屏障：任一成员首个请求须等到另一成员首个请求到达），各自写入均经配置的安全门；重新启用的全局工具 `working_directory` 对领队与成员不可见 |
| it19-acceptance-checker | 完整团队运行后，验收检查器仅凭落盘记录与独立复跑判定通过；伪造的交付 id、点名模型的任务、被改动的工作区文件均判失败 |
| it20-discussion-context | 讨论双方都收到用户原始请求与其中点名的需求文档（自动附上）；`revises` 修订方案时双方都看到上次的必改项；未知的 revises id 被拒绝 |
| it21-task-tools | 任务精确授权、延迟 write、未选 MCP 描述不进入请求、越权加载拒绝；配置扩大后冷恢复不增权 |
| it22-skill-context | 目录只回元数据，只有选中技能正文注入成员；链接资料不自动加载；磁盘正文改变后恢复仍用快照 |
| it23-role-configuration | 五角色全部配置为不同模型系列和档位，实际请求、讨论、裁断及用量记录与配置一致 |
| it24-load-admission | 已完成 load 后核对官方旧步骤仍无 write；同批早期写返回 unknown tool，只有下一步骤写入成功 |
| it25-sandbox-stop | 沙箱初始化失败后收起命令工具、禁止重新加载和重复派发；冷恢复仍保留故障，防止无效重试 |
| it26-untrusted-description | 插件描述中的伪造策略与授权只作为 JSON 数据传给最终安全门；系统提示明确其不可信，真实授权、范围和参数哈希不变；批准的插件主体执行，被拒主体不执行 |
| it27-leader-read-grant | 领队读取工作区与参考根之外的路径默认被硬规则拒绝；用户在本会话消息行首输入 `允许读取 <绝对路径>` 后该路径对领队只读放行，成员仍不继承该授权 |
| it28-workflow-lifecycle | 伪造或已被 `revises` 取代的 `plan_id` 被拒绝；成员完成后状态从 `started`/`running` 更新为 `done`；重复提交同一被拒调用触发去重拦截而不消耗模型审查次数；第二轮用户任务自动重置单任务计划数上限并要求新任务自己的批准计划 |
| it29-elastic-concurrency | 实时调低并发上限（`3 -> 1`）不强杀在途子代理，领队在每步刷新的上下文看到 `draining_above_cap` → `at_capacity` 并自发停派自然回落；领队空闲时实时调高上限（`1 -> 3`）由后台监控自动唤醒领队且不递增 `task_seq`，沿用同一 `plan_id` 补派待命子任务并行执行；治理角色全程不受限 |
| it39–it43 | 滚动规划增量、模型配置写入器、外部计划归档与计时器、真实上游模型容量同步、单次 `max-tokens` 无损续接与熔断调查恢复 |
| it44-autonomous-direct-exec | 自治模式下领队免 `plan_id` 直接派发、`team_direct_exec` 沙箱硬锁拦截越界操作、分层安全门确定性放行（零重复模型调用） |
| it45-arbitration-conference | 双评审一致异议 → 三方 2/3 预议 → 在途成员即时交接检查点暂停屏障 → 二方正式会商与整改实质验证 → 同案第三次异议直接上调人工及 `conferenceId` 世代竞态恢复 |

## B. 真实模型验收

两个真实模型测试脚本默认跳过 `gpt` 家族路由以节省高单价模型配额；确需包含 GPT 路由验证时可显式传入 `--allow-gpt`。

### B1. 四角色契约探测（`scripts/dev/live-role-probe.mjs`）

经官方运行时验证配置中的真实模型和档位：门对正常写入 allow、危险删除 deny；A/B 合规独立意见；裁断只选 A/B；两位评审批准完整包含用户要求的计划（含失败后修复重跑）。保持严格批准判据，不把评审指出测试提案真实遗漏视为随机失败。七项全过才通过；输出逐项记录真实路线、档位、耗时与尝试次数。

### B2. 核心设计整链验收（`scripts/dev/run-live-acceptance.mjs`）

任务（`test/live/e2e-parallel/task.md`）不点名任何执行模型，两个独立模块。`scripts/dev/check-team-acceptance.mjs` 只依据会话日志、团队存储、工作区文件和独立复跑判定 13 项：C01 退出 0 且声称交付通过；C02 声称的交付讨论真实存在且 approve；C03 写入派发前 plan 已通过；C04 领队全程为 `roles.leader`；C05 领队与成员只见档位工具；C06 先 team_models 后派发；C07 任务未点名模型；C08 ≥2 个写入成员均为执行池模型、支持的档位、额度未耗尽且实际运行未被替换；C09 两成员活动时间重叠；C10 每个受控成员操作都有门回执、无 gate-error、审查模型为 `roles.gate`；C11 每个模块都由成员经 shell 实际测试且作业完成、退出 0；C12 检查器独立复跑全部测试通过且数量正确；C13 允许范围外的文件与运行前清单逐字节相同、无新增。

## C. 官方 Desktop 验收

更新发布后的正式窗口冒烟由 `scripts/dev/check-desktop-smoke.mjs` 依据正式 home 的会话日志判定：S1 发布后新建了 LeaderTeam 领队会话；S2 全部请求为 `roles.leader`；S3 领队只见档位工具（无 `working_directory`/`load_workspace_dependencies`）；S4 team_models 成功、`leader_model` 为 match、列出全部执行池；S5 额度行与额度工具 state.json 一致（同一快照逐值相同；快照刷新后结论相同且偏差不超过 10 个百分点）。下列 1–6 为历史手工步骤。

1. 预设列表出现 LeaderTeam 与三个 “LeaderTeam 成员” 预设；启动日志无 Failed plugins。
2. 新建 LeaderTeam 会话（选择配置的 `roles.leader` 模型），让它“列出可用模型”→ 调用 `team_models`，额度状态与额度快照一致。
3. 给一个小任务：能看到 `team_discuss`、`team_dispatch` 卡片；成员会话可在子代理列表中打开；成员写文件时有安全门回执（`<DSH_HOME>\leaderteam\teams\<会话>\gate.jsonl`）。
4. 在普通 `standard` 预设会话里写文件，不产生安全门回执（`scope=team`）。
5. 让成员尝试写 `globalRefRoots` 下的参考文件 → 被拒绝。
6. 关闭并重开 Desktop，继续上一 LeaderTeam 会话，给成员发消息 → 成员仍能按原档位工作。
