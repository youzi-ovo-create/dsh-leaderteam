# LeaderTeam 历代设计原则与反退化工程台账（V1.6 → V2.2.3）

> **台账定位与维护铁律**
> 1. 本文件是 LeaderTeam 长期维护的一等工程资产，用于防止在版本迭代中出现「新机制意外覆盖、架空或遗忘早期已验证设计成果」的版本回归事故。
> 2. 任何涉及 `prompts.mjs`、`gate-policy.mjs`、`runtime.mjs`、`concurrency.mjs`、`planning.mjs`、`model-config-writer.mjs` 或宿主预设 YAML 的修改，合并前必须逐条对照本台账核验。
> 3. **严禁仅用提示词字符串匹配单测代替行为验收**；每条原则均同时约束「设计原意、适用边界、历史翻车案例、真实模型行为验收指标」，且所有修复必须保持模型无关与任务领域无关（严禁针对单一模型家族或单一测试题目编写特化规则）。

## DP-01：渐进式局部就绪规划与分权自治的正交融合（Progressive Readiness × Autonomous Dispatch）

- **确立版本**：V1.9（渐进式滚动规划）+ V2.1（异步监督自治模式）→ V2.2.2+ 正交合并修复
- **设计原意与机制机理**：
  - V1.9 确立「局部就绪即规划完成」：领队**不需要**在第一次工具调用前私下推演整个工程的全部模块细节、接口与边缘情况；只需先记录紧凑全局概览（`overview`），将当前信息已足够支撑实施的首批阶段标为 `ready=true`，下游阶段保留在 `future_work` 或 `ready=false` 随前序产出渐进细化。
  - V2.1 确立「免审批阻塞直接派发」：阶段 `ready=true` 后无需等待双评审返回 `plan_id`，立即通过 `team_dispatch` 派发成员施工，双评审在后台异步监督，仅在双审一致异议且经 2/3 法定人数投票升级时才介入暂停。
  - **两者是正交提速关系（局部规划 → 立即派发 → 后台监督 → 同步规划后续阶段）**，绝非互斥替代关系。
- **适用条件与权力/安全边界**：
  - 适用于所有多阶段工程任务（尤其是零起点开放式工程与中大型多模块任务）。
  - 边界：局部就绪不等于降低单阶段契约质量——任何标为 `ready=true` 的阶段，其自身的 `goal`、`interfaces`、`write_scope` 与 `acceptance` 对承接该阶段的成员必须是决策完备的；未动用争议会商（`phase=normal`）时，不应在首轮提示词中堆砌冗长的会商程序细则干扰首步决策。
- **历史退化与翻车实录**：
  1. `2026-11-17`（V1.8/V1.9 早期测试）：使用深度推理模型担任领队时，因缺少「禁止首步私下完成全项目设计」约束，首步纯推理耗时 `448.7s` 零工具调用，促使 V1.9 在 `rollingLeaderSection` 中专门增设渐进式局部就绪纪律。
  2. `2026-11-26`（V2.1–V2.2.1 回归事故）：`leaderSection` 新增 `if (isAutonomousGovernance(config)) return autonomousLeaderSection(...)` 分支时直接提前返回，跳过了 `rollingLeaderSection`，导致 V1.9 的局部就绪与边跑边规划纪律被静默丢弃。在 `GPT-6.2 Sol`（单步短推理习惯，140 步平均输出约 `356` Tokens）的存量仓测试中该缺陷被模型自身习惯掩盖；但在切换至深度推理大陆模型执行零起点开放工程时，Step 1 单步私有推理长达 `468.9s`（`118,884` 字符），23 分钟内未能发出首个正式阶段派工。
- **行为级验收判据与自动化防线**：
  - **代码防线**：当 `rollingPlanning === true` 且 `governance.mode === "autonomous"` 时，领队提示词与 `formatFrontierContext` 必须同时包含局部就绪边界（禁止首步私下完成全工程设计、允许先派发首批就绪阶段并重叠规划后续阶段）与异步监督自治规则；冗长的二方会商应答细则仅在 `pausingConference` / `activeConference` 实际激活时按需注入。
  - **真实模型行为验收**：在深度推理大陆模型（如 `GLM` / `Qwen` / `DeepSeek` 高推理档位）执行零起点开放工程时，首轮工具调用（`overview` / 首批探索或阶段定义）应在合理冷启动窗口内发出，并在无需跑完全局细化的前提下完成首批 `team_dispatch` 实际派发。

## DP-02：环境事实保真与安全门拒绝语义严格分离（Host Facts Fidelity vs. Policy Denial Semantics）

- **确立版本**：V2.2.2+（吸取 V2.2 直执沙盒锁次生误导教训）
- **设计原意与机制机理**：
  - 安全门拦截越界调用时，**「当前角色无权限探测某外部路径/网络」与「宿主机上不存在该程序/字体/资源」在认识论上是完全不同的两件事**。
  - 若拒绝回执或子代理汇报将权限拦截模糊化，领队会形成错误的宿主机世界模型，进而基于错误前提展开灾难性的替代方案推演。
  - 同时，对于常规软件工程普遍依赖的宿主基础工具链事实（操作系统架构、Node/npm/pnpm/Python/Git/Cargo 可用性、标准路径下是否存在 Chromium/Edge/Chrome 浏览器可执行文件），应由宿主运行时在会话初始化时以只读、脱敏（不含用户名隐私路径与任何密钥）、静态摘要的形式直接提供给领队，避免模型浪费子代理轮次去盲探受保护的系统目录。
- **适用条件与权力/安全边界**：
  - **绝不因便利性放开安全边界**：`direct_exec` 继续严格锁定在工作区沙盒内，禁止任意读取工作区外宿主机文件（如 `~/.ssh`、`.credentials.yaml`、系统配置等），禁止未授权破坏性命令。
  - 所有边界类拒绝回执必须显式携带语义声明：该拒绝仅表示**当前角色的沙盒/权限策略禁止此访问**，不代表目标程序、路径或网络资源在宿主机上缺失；需要宿主外部工具链执行时应结合宿主静态工具链摘要，或交由经契约与安全门审查的 `shell` 阶段成员执行。
- **历史退化与翻车实录**：
  - `2026-11-26`（V2.2.1 开放工程事故）：领队派 `direct-exec-1` 探测 `C:\Program Files\...\msedge.exe` 与 `C:\Windows\Fonts\msyh.ttc` 被 `rule:direct-exec-sandbox-lock` 拒绝，退而执行 `Get-Command chrome.exe,msedge.exe` 因 Windows 浏览器不在 `PATH` 中返回空；领队据此误判宿主机不存在任何浏览器，为兑现截图验收承诺，在 Step 3 耗费 **11 分钟（`122,327` 字符推理）**从零手推多边形扫描线软光栅 2D 渲染引擎与 Alpha 混合公式。
- **行为级验收判据与自动化防线**：
  - **代码防线**：单测验证所有 `direct-exec-sandbox-lock` 回执均包含明确的「权限边界 ≠ 资源缺失」说明；验证宿主静态工具链探针在零外部子进程弹窗条件下准确生成脱敏布尔/版本摘要且在整场会话内保持静态不变。
  - **真实模型行为验收**：在需要本地构建/浏览器验证的开放工程中，领队直接读取宿主环境摘要即可获知本机工具链可用性，不再派 `direct_exec` 盲撞 `C:\Program Files`，更不会因误判环境缺失而推导离奇的替代造轮子方案。

## DP-03：受宿主权限管辖的原生只读联网调研能力对齐（Authorized Native Web Research Parity）

- **确立版本**：V2.2.2+
- **设计原意与机制机理**：
  - 在开放式研发任务（查阅公开标准、API 文档、第三方库用法或领域规则）中，编排系统不应比原生单 Agent 更「失明」。DSH 宿主原生提供的 `@deepseek-ai/dsh-tool-web`（`web_search`、`web_fetch`）已具备超时控制与非授信外部内容隔离包装，应正式挂载至桌面/Web 预设（`leaderteam`、`lt-member-readonly`、`lt-member-shell`）并纳入工具策略。
- **适用条件与权力/安全边界**：
  - **严格遵循用户任务授权**：当用户提示词明确禁止联网（如包含「禁止联网」「不得联网」「离线完成」「offline only」「no network」等约束）时，安全门确定性规则直接以 `rule:network-forbidden-by-user` 拦截 `web_search` 与 `web_fetch`；当用户未禁止或明确允许联网时，`0ms` 确定性放行公开 `http(s)` 只读检索（并严格阻断内网/本地回环 SSRF）。
  - 离线脚本化集成测试（`headless.patch.yml`）保持 `tool-web` 默认停用，确保离线回归夹具 100% 封闭可复现。
- **历史退化与翻车实录**：
  - `2026-11-26`：同一模型在原生 DSH `standard` 预设下 3 分钟内通过 `web_search` + `web_fetch` 准确查清全部关卡规则；切入 LeaderTeam 后因预设白名单漏挂 `tool-web` 且 `direct_exec` 禁网，模型被迫凭记忆硬猜并发生事实性张冠李戴。
- **行为级验收判据与自动化防线**：
  - **代码防线**：单测覆盖桌面预设包含 `@deepseek-ai/dsh-tool-web`、`profiles.{leader,readonly,shell}.tools` 支持 `web_search`/`web_fetch`，以及用户禁网指令与内网 SSRF 地址下的安全门确定性拦截。
  - **真实模型行为验收**：在允许联网的开放工程任务中，领队或只读调研成员能正常使用原生搜索获取准确外部资料，零无谓绕行。

## DP-04：上下文注入动静严格分离与静默抑制（Static/Dynamic Context Separation & Quiescent Suppression）

- **确立版本**：V1.9 复盘确立 → V2.2 局部复发 → V2.2.2+ 全面收口
- **设计原意与机制机理**：
  - DSH 的 `systemPrompt.context` 机制会在返回文本发生哪怕 1 个字符变化时，向会话消息流追加新的 `<system-reminder>` 快照。若在每步调用的上下文函数中混入随每次请求递增的计数器或秒级计时器，会导致每一步都破坏前缀 KV 缓存并加速触发同步上下文压缩（Compaction）。
  - **静态信息放 `section`，动态信息按域独立拆分为多个 `context`，且常态无变化（如 `phase=normal`、无预警、计数未跨档位）时输出完全恒定的文本或空串**。
- **适用条件与权力/安全边界**：
  - 适用于所有挂入 `agent.ctx.systemPrompt.context` 的回调（规划前沿、并发调度、异步治理、计时归档）。
  - 边界：当真实状态发生变化（如 `effective_cap` 扩缩、请求窗口进入 `elevated`/`critical`/`pause` 预警档、出现双审建议或正式会商、计时压力升档）时，必须立即准确呈现最新状态，不得因缓存优化隐瞒实质状态变迁。
- **历史退化与翻车实录**：
  1. `2026-11-17`（V1.9 事故）：`planning.mjs` 在每步阶段 JSON 中附带秒级变动的 `elapsed` 字段，单场会话刷出 `192` 份上下文快照、触发 `67` 次同步压缩（耗费 `79.3` 分钟，占总墙钟 `53.4%`）。
  2. `2026-11-25`（V2.2 Linux 自举观测）：`concurrency.mjs` 在每步注入 `local_estimated_requests_5h` 逐次递增整数，并与治理、计时器拼在同一返回串中，导致每步重新注入上下文块。
- **行为级验收判据与自动化防线**：
  - **代码防线**：单测连续模拟多次模型请求（不跨限流档位、不改并发槽位），断言 `formatLeaderConcurrencyContext`、`formatLeaderGovernanceContext` 与 `formatLeaderTimerContext` 返回字符串**逐字节恒定不变**，且三者在 `roles.mjs` 中各自独立注册 `context` 槽位互不牵连。
  - **真实模型行为验收**：实跑会话日志中输入缓存命中率保持高位，无因计数跳变引发的每步重复 `<system-reminder>` 注入。

## DP-05：开工前配置可热同步、开工后治理快照冻结，且保留 `enforce` 校验与诊断通道（Deferred Governance Freeze & Enforce Integrity）

- **确立版本**：V1.6（领队模型强校验与团队治理不可篡改）→ V2.2.2+ / V2.2.3（修复桌面端空会话复用死锁并与会话级跟随策略正交共存）
- **设计原意与机制机理**：
  - `governance.json` 快照的设计目的是保证**团队一旦正式开始规划或派工**，中途外部修改全局配置不会破坏在途任务的治理规则与审计一致性。
  - 当会话启用 `leaderModelPolicy: "follow"` 时，会话级模型选择自动隔离同步至 `session-config.json`；当用户或团队显式配置 `leaderModelPolicy: "enforce"` 时，严格阻止错位模型执行编排副作用。
  - 正确的生命周期边界是：**尚未产生任何规划、成员派发或治理事件的空白会话（未开工状态）不冻结旧快照，始终跟随最新保存的配置并在保存时自动同步空白会话的默认领队模型；一旦首个规划或执行动作发生，立即原子落盘冻结 `governance.json`**。
  - 同时，即便在 `enforce` 拦截状态下，也必须放行受阻状态上报（`team_status` 的 `blocked`/`waiting_user` 上报），并在内置控制台提供清晰的不一致提示与一键对齐入口。
- **适用条件与权力/安全边界**：
  - 边界：`enforce` 拦截下，任何会产生规划或执行副作用的工具（`team_plan`、`team_dispatch`、`team_direct_exec`、`team_discuss`、`team_note`、`team_status("delivered"|"waiting_members")`）依然 100% 严格阻断，绝不开后门。
- **行为级验收判据与自动化防线**：
  - **代码防线**：单测验证：（1）空会话选预设 → 控制台改领队与角色保存 → 未开工会话自动热绑定新配置；（2）开工后修改全局配置，在途会话的 `governance.json` 保持冻结不被篡改；（3）`enforce` 下模型不匹配时，`team_models`/`team_dispatch` 被拦截，但 `team_status(stop_state="blocked")` 可正常诊断上报，控制台可一键双向修复对齐。

## DP-06：成员执行池与回退链的协同一致性维护（Execution Pool & Fallback Co-Maintenance）

- **确立版本**：V2.2.2+
- **设计原意与机制机理**：
  - `validateConfig` 要求 `team.executionFallbacks` 中的主键与候选目标均属于已启用的 `team.executionPool`，这是防止回退到被用户禁用的模型的合理不变量。
  - 因此，配置写入器（`applyModelConfigChanges`）与图层合并器（`mergeConfigLayers`）在用户通过 UI 或 CLI 缩减 `executionPool`（`poolSet`、`poolDisable`、`poolDisableFamilies`、`removeModels`）时，必须**自动协同修剪 `executionFallbacks` 中已被移出执行池的路由**并记录变更提示，而不是把内部关联清理负担抛给用户报错。
- **历史退化与翻车实录**：
  - `2026-11-26`：用户在内置控制台取消勾选部分成员池模型仅保留单模型施工时，因底层 `executionFallbacks` 仍残留被取消模型的映射，点击保存直接弹出整屏校验错误。
- **行为级验收判据与自动化防线**：
  - **代码防线**：单测覆盖存在复杂多层 `executionFallbacks` 时，在 `base` 与 `local` 两种目标下取消勾选任意模型或仅保留单一模型均可一次保存成功且配置合法。
