# 跨平台独立发行与长期工程治理规范（Linux & Windows）

本文档定义 `dsh-leaderteam` 项目的长期跨平台研发协同、代码分层、独立平台适配与 GitHub Release 标签治理规范。

---

## 一、核心工程治理原则

1. **共享技术内核与公共契约（Shared Core & Contracts）**：
   - Windows 与 Linux **共享**全部核心治理算法、历代设计原则（`DP-01`..`DP-06`，详见《[历代设计原则与反退化台账](12-历代设计原则与反退化台账.md)》）、公共 HTTP 契约（`lt.public.v1`）、模型路由与会话隔离机制（`session-config.mjs` / `session-mode.mjs`）、四桶物理 Token 账本及通用缺陷修复。
2. **Linux 技术先行，双平台独立适配与独立发行（Independent Platform Adaptation & Release）**：
   - 以 **Linux** 作为核心架构与新特性的技术先行验证平台；
   - **Windows** 随后按对应技术目标完成本平台专属适配（如 NTFS 重解析点/Junction、Win32 进程树生命周期、桌面端 `app.asar` 与注册表寻址、沙箱 ACL 及终端通道熔断）；
   - Windows 与 Linux **各自独立进行平台适配、日常维护、回归验收与正式发版**，**双方不强制同步发版**；任一平台在完成自身全量质量门禁后即可独立发布该平台 Release，无需等待另一平台同步阻塞。
3. **单一公开仓库 + 平台前缀 Release 标签隔离**：
   - 开源维护版继续统一使用公开仓库 [`youzi-ovo-create/dsh-leaderteam`](https://github.com/youzi-ovo-create/dsh-leaderteam)（`Apache-2.0`），开闭源边界保持严格物理隔离；
   - 同一仓库内通过 **`linux-vX.Y.Z`** 与 **`windows-vX.Y.Z`** 区分两个平台的正式 Release。

## 二、GitHub Release 标签规范与防串台机制

### 1. 标准 Release Tag 命名规范

| 目标运行平台 | Release Tag 格式 | 示例 | 制品说明 |
|---|---|---|---|
| **Linux** (`linux`) | `linux-vX.Y.Z` | `linux-v2.2.3`、`linux-v2.2.4` | 经 Linux 环境全量验收的 `dsh-leaderteam-X.Y.Z.tgz`、`install-leaderteam.sh` 与 `SHA256SUMS.txt` |
| **Windows** (`win32`) | `windows-vX.Y.Z` | `windows-v2.2.3` | 经 Windows 环境全量验收的 `dsh-leaderteam-X.Y.Z.tgz`、`Install-LeaderTeam.cmd`、`lt-installer-standalone.mjs` 与 `SHA256SUMS.txt` |
| 历史兼容标签 | `vX.Y.Z` | `v2.2.0` | 仅作为早期无平台前缀归档版本的向后兼容回退 |

### 2. 安装器与自动更新器的防串台硬规则

由于 Linux 与 Windows 不强制同步发版（例如远端仓库最新发布的 Release 可能是 `linux-v2.2.4`，而当前 Windows 最新稳定版为 `windows-v2.2.3`），`leaderteam/core/updater.mjs`、`leaderteam/core/installer.mjs`、`bin/lt-installer.mjs` 与 `installer/lt-installer-standalone.mjs` 强制执行以下筛选与校验契约：

1. **严禁盲取 `/releases/latest`**：客户端检查更新与在线下载时，统一拉取 `/releases` 列表并按当前操作系统平台（`process.platform`）执行确定性过滤。
2. **同平台前缀优先、异构平台硬隔离**：
   - 在 **Windows (`win32`)** 上：**绝不匹配 `linux-vX.Y.Z`**；当列表中存在 `windows-vX.Y.Z` 时仅从 `windows-v*` 中选取最高 SemVer 版本；仅当仓库内尚无任何 `windows-v*` 标签时才向后兼容回退历史无前缀 `vX.Y.Z`。
   - 在 **Linux (`linux`)** 上：**绝不匹配 `windows-vX.Y.Z`**；当列表中存在 `linux-vX.Y.Z` 时仅从 `linux-v*` 中选取最高 SemVer 版本；仅当仓库内尚无任何 `linux-v*` 标签时才向后兼容回退历史无前缀 `vX.Y.Z`。
3. **显式跨平台标签硬拦截（`PLATFORM_RELEASE_TAG_MISMATCH`）**：
   - 若调用方通过 CLI（如 `lt-update --version linux-v2.2.3` 或 `lt-installer --version linux-v2.2.3`）或 API 在 Windows 上显式指定 `linux-v*` 标签（或在 Linux 上指定 `windows-v*` 标签），系统将在下载前立即抛出 `PLATFORM_RELEASE_TAG_MISMATCH` 错误并中止操作。

## 三、Git 提交分层规范（Universal vs Platform-Specific Commits）

为确保 Linux 与 Windows 维护线能够低摩擦互摘通用研发成果而不引入异构平台副作用，日常研发与发版分支须遵循**双层提交分离规范**：

1. **通用层提交（Universal Commits）**：
   - **范围**：治理状态机（`governance*.mjs`）、角色路由与模型发现/同步（`role-routes.mjs`、`upstream-models.mjs`、`onboarding.mjs`、`session-config.mjs`）、双模控制（`session-mode.mjs`、`mode-controller.mjs`）、历代设计原则（`DP-01`..`DP-06`）、公共 API 契约（`lt.public.v1`）、跨平台 Release 标签解析器及通用架构文档。
   - **前缀建议**：`fix(kernel,dp): ...`、`feat(onboarding,updater): ...`、`fix(governance): ...`。
   - **跨平台要求**：保持零平台专属副作用，使另一平台维护者可直接 `git cherry-pick` 合入。
2. **平台适配层提交（Platform-Specific Commits）**：
   - **Windows 专属适配范围**：Windows 宿主终端初始化异常熔断（`0xC0000142` / `STATUS_DLL_INIT_FAILED`）、NTFS Junction / 重解析点路径归一、Windows 注册表 `Uninstall` 与 `C:..Z:` 全盘自定义目录探测、`Install-LeaderTeam.cmd`、Windows 下 Magpie 进程树回收（`taskkill /T /F` 兜底）及 Windows 专属单测修复。
   - **Linux 专属适配范围**：Linux `/proc` 与层级化 `cgroup v2/v1` 资源探针、`bwrap` 沙箱与 POSIX shell 边界、`systemd` 守护协同及 `install-leaderteam.sh`。
   - **前缀建议**：`feat(windows): ...` / `fix(windows): ...` 或 `feat(linux): ...` / `fix(linux): ...`。
   - 每次平台独立发版时，随交付物附带《提交分层清单》（`COMMIT-LAYERING-MANIFEST.md`），明确列出可供对端平台直接摘取的通用 Commit SHA 与本平台专属适配 Commit SHA。
