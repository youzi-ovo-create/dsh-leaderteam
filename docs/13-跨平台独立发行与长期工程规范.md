# 跨平台独立发行与长期工程治理规范（Linux & Windows）

本文档确立 `dsh-leaderteam`（开源维护线，`Apache-2.0`）在 **Linux** 与 **Windows** 双一等公民平台上的长期研发协作、Git 分层提交、独立验收与异步发行治理规范。

---

## 一、核心治理原则

1. **共享技术底座与核心契约（Shared Core & Contracts）**：
   - Linux 与 Windows **100% 共享**核心治理状态机（四阶段分权自治、双盲有责评审、独立裁断、熔断调查员）、确定性宿主安全门规则、历代设计原则（`DP-01`..`DP-06`）、公共前后端契约（`lt.public.v1`）、四桶物理 Token 账本以及平台无关的通用缺陷修复（Universal Fixes）。
2. **平台独立适配、独立验收与异步发版（Independent Platform Adaptation & Release）**：
   - 以 **Linux 作为技术先行验证平台**，Windows 随后按对应技术里程碑完成宿主协议、NTFS 沙箱/重解析点、进程生命周期与图形化安装器适配；
   - **双方不强制同步发版**：任一平台完成本平台真机闭环验收即可独立发布该平台版本，无需等待另一平台同步阻塞，也无需在单一平台发版窗口内承担跨平台回归签字责任。
3. **开闭源仓库边界不变**：
   - 开源维护线继续统一使用公开仓库 [`youzi-ovo-create/dsh-leaderteam`](https://github.com/youzi-ovo-create/dsh-leaderteam)（`Apache-2.0`），通过平台前缀 Release 标签区分各平台正式发行制品。

---

## 二、Git 提交分层规范（Universal vs Platform-Specific Commits）

为保证 Linux 与 Windows 分支能够低摩擦、零污染地双向摘取（`git cherry-pick`）研发成果，所有工程修改在 Git 提交历史中**必须严格分层为独立 Commit**，严禁将平台专属补丁与通用内核修复混入同一提交：

| 提交层级 | 建议 Commit 前缀 | 包含范围 | 跨平台摘取策略 |
|---|---|---|---|
| **通用修复与特性层（Universal Layer）** | `fix(v2.2.x): ...` / `feat(v2.2.x): ...` / `fix(kernel,dp,usage): ...` | 治理协议、调度器算法、`DP-01`..`DP-06`、`lt.public.v1` 公共 API、河洛 Web 工作台、DSH `0.2.2-rc.1+` 通用模型同步与单会话隔离配置 | Linux 与 Windows **双向直接摘取** |
| **Windows 平台专项层（Windows-Specific Layer）** | `feat(windows): ...` / `fix(windows): ...` | `Install-LeaderTeam.cmd`、Windows 注册表与全盘自定义路径扫描（如 `D:\Apps\DeepSeek-Harness`）、零状态 `profiles/desktop` 初始化、NTFS Junction/重解析点路径归一、`0xC0000142` Shell 通道熔断器、`magpie-cli.exe` 优先级与跨进程 PID 保活守卫 | Windows 发行线专属维护（Linux 线无需强合，纯逻辑门控代码保持跨平台无害） |
| **Linux 平台专项层（Linux-Specific Layer）** | `feat(linux): ...` / `fix(linux): ...` | `cgroup v2/v1` 容器配额细节、`bwrap` 命名空间诊断、`/proc/<pid>` 同步进程树审计与 Systemd 托管脚本 | Linux 发行线专属维护 |
| **发行文档与版本封板层（Release Docs Layer）** | `docs(release): ...` | `CHANGELOG.md`、平台发行说明与分层核验清单 | 按平台发版节奏独立封板打标 |

## 三、Release 标签命名与防串台机制（Anti-Cross-Contamination）

### 1. 标准标签格式

同一仓库下通过操作系统前缀区分平台正式版 Release 标签，同时向后兼容历史无前缀标签：

- **Linux 发行标签**：`linux-vX.Y.Z`（例如 `linux-v2.2.2`、`linux-v2.2.3`）
- **Windows 发行标签**：`windows-vX.Y.Z`（例如 `windows-v2.2.2`、`windows-v2.2.3`）
- **历史兼容标签**：`vX.Y.Z`（例如 `v2.2.0`、`v2.2.1`，仅在目标仓库尚无当前平台前缀 Release 时作为回退匹配）

### 2. 自动更新器与一键安装器的平台隔离硬规则

由于 Linux 技术先行、双平台异步发版（例如远端仓库可能同时存在已先行发布的 `linux-v2.2.4` 与当前 Windows 最新稳定版 `windows-v2.2.3`），`leaderteam/core/updater.mjs`、`leaderteam/core/installer.mjs`、`bin/lt-installer.mjs` 与 `installer/lt-installer-standalone.mjs` 强制执行以下四条防串台不变量：

1. **严禁盲目请求 `/releases/latest`**：GitHub `/releases/latest` 仅返回全仓时间最新的一条 Release，异步发版下极易指向另一平台。所有检查更新与在线安装统一拉取 `/releases` 列表并在本地按运行平台严格过滤（即使外部传入自定义 `apiUrlOverride` 指向 `/releases/latest`，也会自动重写为 `/releases` 列表查询）。
2. **同平台前缀优先、严禁匹配异构平台**：
   - 在 **Windows (`win32`)** 上：彻底剔除所有 `linux-v*` 条目；若存在 `windows-vX.Y.Z` 则仅在 `windows-v*` 中选取最高语义化版本，仅当尚无任何 `windows-v*` Release 时才回退匹配历史无前缀 `vX.Y.Z`。
   - 在 **Linux (`linux`)** 上：彻底剔除所有 `windows-v*` 条目；若存在 `linux-vX.Y.Z` 则仅在 `linux-v*` 中选取最高语义化版本，仅当尚无任何 `linux-v*` Release 时才回退匹配历史无前缀 `vX.Y.Z`。
3. **显式跨平台标签硬拦截（`PLATFORM_RELEASE_TAG_MISMATCH`）**：
   - 若通过 CLI（`--tag`）、API（`releaseTag`）或下载链接显式传入异构平台标签（例如在 Windows 上指定 `linux-v2.2.2`，或在 Linux 上指定 `windows-v2.2.2`），安装器与升级器立即抛出 `PLATFORM_RELEASE_TAG_MISMATCH`（HTTP `409`）拒绝执行，绝不下载或覆盖本地环境。
4. **平台隔离缓存**：本地更新检查缓存按 `check-cache-<track>-<platform>.json` 分平台落盘，杜绝 WSL2 与宿主机共用目录或跨平台迁移时的缓存串台。

## 四、单平台独立发版核验清单

每次发布 `windows-vX.Y.Z`（或 `linux-vX.Y.Z`）前，当值平台发布工程师须完成以下闭环核验：

1. **版本契约边界核对**：确认 `package.json`、`leaderteam/package.json`、`lt.public.v1` `contractVersion` 及能力特性开关（如 `v2.2.2` 保持 `contractVersion: "1.0.1"` 与 `inSessionDualMode: false`）准确无误。
2. **分层提交审查**：`git log` 清晰区分 Universal 修复提交与当前平台专属适配提交，附带分层修复清单（`RELEASE-LAYERS-<platform>-vX.Y.Z.md`）。
3. **隔离环境全量测试**：在完全隔离的临时目录（严禁读写开发者个人 `~/.dsh`）中通过本平台全部单元测试、公共契约校验与 `.tgz` 打包自检。
4. **开源纯净度与完整性校验**：确认零 `.node` 闭源二进制、零私有目录引用，生成标准 `dsh-leaderteam-X.Y.Z.tgz`、独立安装器与 `SHA256SUMS.txt`，并在验收通过后打上 `<platform>-vX.Y.Z` 标签。
